# Aider Instructions & Coding Conventions

You are editing the **civictech-crypto-engine**, an enterprise-grade cryptographic engine for CivicTech applications built with **Spring Boot 3.3.0**, **Java 21**, and **Maven**.

Adhere strictly to the architectural and coding conventions described below:

---

## 1. Language & Framework Conventions
- **Java 21 Standards**:
  - Leverage modern Java features such as **Records** for DTOs, pattern matching for `instanceof`, `switch` expressions, text blocks, and the stream API.
  - Class names must be `PascalCase` (e.g., `VotingController`).
  - Variable and method names must be `camelCase` (e.g., `generateKeyPair`).
  - Package names must be lowercase (e.g., `com.civictech.crypto.engine.vault.dto`).
- **Dependency Injection**:
  - Always use **Constructor Injection** for Spring beans. Do **not** use field-level `@Autowired` injection.

---

## 2. API & DTO Conventions
- **Data Transfer Objects (DTOs)**:
  - Implement DTOs as Java **Records**.
  - Explicitly annotate every field of a DTO record using `@JsonProperty("field_name_in_snake_case")` (e.g., `@JsonProperty("file_checksum") String fileChecksum`).
- **Input Validation**:
  - Use `jakarta.validation.constraints` (e.g., `@NotEmpty`, `@NotNull`, `@Min`) on the DTO record parameters.
  - Implement a **compact constructor** on the record for compound validation or conditional validation rules, throwing an `IllegalArgumentException` if the validation fails:
    ```java
    public SignRequest {
        if ((fileChecksum == null || fileChecksum.isBlank()) && (payloadBase64 == null || payloadBase64.isBlank())) {
            throw new IllegalArgumentException("Either 'file_checksum' or 'payload_base64' must be provided.");
        }
    }
    ```
- **Serialization**:
  - The API expects and produces JSON with `SNAKE_CASE` property names (configured via Jackson settings in `application.yml`). Ensure custom serialization adheres to this.

---

## 3. Web & Security Architecture
- **API Versioning & Controllers**:
  - Map all REST endpoints under `/v1/` (e.g., `/v1/voting`, `/v1/vault`).
  - Controllers must be annotated with `@RestController` and `@RequestMapping("/v1/...")`.
  - Use appropriate HTTP methods (e.g., `POST` for actions/mutations, `GET` for retrieval).
- **Authentication**:
  - The application is protected by a stateless API Key authentication filter (`ApiKeyAuthFilter`).
  - All endpoints except `/v1/health` and `/v1/voting/static/**` require the request header: `Authorization: Bearer <api-key>`.
  - If you add a new endpoint, it will be automatically protected by Spring Security under `/v1/**` unless explicitly configured in `SecurityConfig` and `ApiKeyAuthFilter#shouldNotFilter`.

---

## 4. Cryptographic Standards
- **Bouncy Castle Provider**:
  - The Bouncy Castle provider is registered globally in the application main entrypoint (`CivicTechCryptoEngineApplication`).
  - Always request cryptographic instances with the Bouncy Castle provider name (e.g., `Signature.getInstance("SHA256withECDSA", BouncyCastleProvider.PROVIDER_NAME)` or `Cipher.getInstance("AES/GCM/NoPadding", BouncyCastleProvider.PROVIDER_NAME)`).
- **Secrets & Configuration**:
  - Never hardcode cryptographic keys, credentials, or API tokens.
  - Bind custom keys and external variables via `@Value` or `@ConfigurationProperties` to the `crypto` or `voting` namespaces in `application.yml`. Allow overriding via environment variables.

---

## 5. Exception & Error Handling
- **Global Exceptions**:
  - All REST endpoints leverage `GlobalExceptionHandler` (`@RestControllerAdvice`).
  - Map specific exceptions to these HTTP statuses:
    - `CryptoException` -> `400 Bad Request` ("Cryptographic Operation Error")
    - `SignatureException` -> `400 Bad Request` ("Signature Verification Failure")
    - `IllegalArgumentException` -> `400 Bad Request` ("Invalid Argument")
    - `MethodArgumentNotValidException` -> `400 Bad Request` ("Validation Failure")
    - `GeneralSecurityException` (low-level Bouncy Castle issues) -> `500 Internal Server Error` ("Security Provider Error")
    - `Exception` -> `500 Internal Server Error` ("Internal Server Error")
- **Standard Error Payload**:
  - Return all errors using the `ErrorResponse` record structure, which maps to:
    ```json
    {
      "timestamp": "ISO-8601 UTC timestamp",
      "status": 400,
      "error": "Error Category",
      "message": "Detailed error explanation",
      "path": "/api/v1/..."
    }
    ```

---

## 6. Testing Practices
- **Test Placement**: Place all unit and integration tests under `src/test/java` matching the packaging structure.
- **Framework**: Use JUnit 5 and Mockito.
- **Verification**: Ensure all tests run green before completing tasks. Execute `mvn test` to verify.
